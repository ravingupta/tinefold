# Brainstorm Tool PRD v0

Oct 24, 2026 · @Ravin Gupta

## Problem statement (root v2)

Build an AI-driven brainstorming tool for IT/software problems. The user states a problem; the AI proposes solution options; each chosen solution breaks into sub-problems, which the AI expands again. The result is an AND-OR graph: problems where one solution is picked, solutions where every sub-problem must be solved.

The AI expands nodes; the user controls every selection. No backend is required: the app runs in the browser, stores each graph as a document plus an event log, and calls LLM providers directly with the user's own API keys. A default provider applies, with per-stage overrides (expansion, classification, stale check).

Later the tool is open source, so others can attach their own models and task types (classify, describe, plan).

## Users and scope

MVP serves one person: the author, using it to brainstorm their own software problems and to learn the AI mechanics by building them. One user per graph; no accounts, sharing or sync.

Second audience, after MVP: engineers who run the open-source build themselves and plug in their own providers and task types. Nothing in MVP may block that, but nothing is built for it yet.

## Core model

The graph has three node types. A problem is answered by picking one child; a solution is complete only when every child problem is resolved; a clarification narrows the context without expanding the graph.

| Node type | Children | User action | Effect |
| --- | --- | --- | --- |
| Problem (OR) | Solution options | Select one | Children of the selected solution become active |
| Solution (AND) | Sub-problems, all required | None | Complete when every sub-problem has a selected solution |
| Clarification (OR) | Answer options + free text | Answer one | Adds a constraint to context; no new nodes |

Selection semantics:

- Selections are the only stored state per problem. Enabled/disabled is derived: a node is enabled if reachable from the root through selected edges.
- The active area is a subtree, not a path, because every sub-problem under a selected solution is active at once.
- Generated nodes are immutable and versioned. Regenerating creates a sibling version; it never overwrites.
- Each expansion returns one of: clarify, solutions, subproblems, leaf. The same JSON contract serves all four, with items, a differentiating axis, a recommendation, a suggested next sub-problem, and any assumptions the model made instead of asking.

## Design constraints

Standing rules agreed before the session. They apply to every decision below.

1. Persist decisions, derive everything else. Selections are source of truth; visibility, the decision summary and the PRD are derived views.
2. Derived views carry a hash of their inputs. A changed hash means stale, never silently wrong.
3. Staleness has two tiers. Red: an ancestor selection or the root changed, so descendants are certainly stale. Yellow: a sibling decision or a comment changed, so possibly stale; a cheap LLM check resolves it on open. Mark eagerly, regenerate lazily.
4. Comments are global amendments to the root problem. Small ones append; ones that change a constraint become a proposed root rewrite the user approves, which creates a new root version and marks the whole tree red.
5. The decision summary that feeds every LLM call is rendered by code from the selected subtree, never by an LLM, so it cannot drift. The PRD is generated by an LLM on demand and cached on the context hash.
6. The LLM may ask instead of expand: if a missing fact would change the options, it emits a clarification node first.
7. Context compilation is deterministic. Same state in, same bytes out, or the hash-based staleness breaks.

## Decisions

Four decisions are selected. Each is the one child of its problem node that is active; the alternatives remain in the graph, disabled.

| Problem | Selected | Alternatives (disabled) | Why |
| --- | --- | --- | --- |
| Root: runtime host | Browser-only SPA: static site, IndexedDB, direct provider calls | Browser + optional thin server; desktop shell (Tauri/Electron) | Matches "no backend required" without an abstraction for a server that may never exist. Revisit a desktop shell before building a proxy if local models become real. |
| Storage model | Document per graph + append-only event log, in IndexedDB | Relational tables; pure event-sourced with replay | One user, UI loads the whole graph; derive-on-read in memory. Ported from the server-backed tree. |
| Expansion contract | Adapter per provider: native structured output where available, prompted JSON + schema validation as fallback | Model-agnostic prompted JSON only; two-phase reason-then-extract | The adapter boundary is needed for the provider registry anyway. Validate even enforced output: schema guarantees shape, not sense. |
| Context compilation | Full context, token count logged per call, hard ceiling; past the ceiling, swap the decision summary for an LLM condensation cached on hash | Relevance-filtered via embeddings | Hundreds of nodes fit easily. The token log says when filtering becomes necessary, with numbers. |

Context for every expansion call = root (current version) + comments + code-rendered decision summary of the active subtree + this node's ancestor chain.

## Assumptions

Facts the engine assumed instead of asking, or where the user answered "I don't know". Correcting any of these is a comment; it marks dependent nodes yellow.

| Assumption | Chosen default | If wrong |
| --- | --- | --- |
| Graph size | Hundreds of nodes per graph, not thousands | Context compilation needs relevance filtering earlier |
| Provider support | Anthropic or OpenAI; both enforce output schemas | Fallback path (prompted JSON) carries more load |
| No backend | Soft: not required, optional later | If hard, drop the "optional server" alternative entirely |
| Models | API keys only for MVP; local models (Ollama, LM Studio) later | Local models bring per-server CORS setup, or a desktop shell |
| Per-stage providers | One default provider, per-stage overrides | Manual per stage adds config burden; single model loses the cost lever |

## Non-goals for MVP

- Accounts, sharing, real-time collaboration, sync between devices
- A server of any kind, including a proxy for providers
- Local model support
- Node sharing across branches (same sub-problem under two solutions). Decisions port by hand via a ported\_from link; automatic merge waits until the identity rule (problem text + inherited constraints) is designed
- Per-node notes. Comments are global only
- Relevance filtering of context via embeddings

## Repository structure

Decision added 2026-10-24: the engine and the web client are separate repositories. The engine is a published TypeScript package that owns every rule in this PRD; the client is a rendering system over it. The two specs below are the handover documents for Claude Code.

| Repo | Owns | Spec |
| --- | --- | --- |
| brainstorm-engine | Event log, reducer, selectors, context compiler, expansion contract, provider adapters, staleness, PRD generation | Brainstorm Engine Spec |
| brainstorm-web | React outline and canvas, IndexedDB adapter, settings and keys, deploy | Brainstorm Web Client Spec |

The engine never imports a UI or a database. The client never computes a graph fact. A feature the client needs and the engine lacks is an engine change first.

## Handover sequence for Claude Code

Run one milestone per session, engine before client, in this order. Give each session the PRD, the relevant spec, and its CLAUDE.md.

1. Engine E0, E1: contract and reducer, with the design-session fixture replaying green. Nothing else until this passes.
2. Client C0, C1: scaffold and a read-only outline rendering the same fixture. This proves the boundary.
3. Engine E2, E3: context compiler, providers, first real expand from a Node script.
4. Client C2, C3, C4: interactions, persistence, expand with a real key. The tool is now usable.
5. Engine E4, E5, E6: staleness, root rewrite and porting, PRD generation.
6. Client C5, C6: staleness UI and the PRD panel.
7. Engine E7, then client C7, C8: publish, canvas, deploy.

First instruction in every engine session: write or extend the fixture test before implementing. First instruction in every client session: render from the fixture before adding the interaction.
